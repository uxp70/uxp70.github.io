Colophon

How this site was made.

The projects on this site are hand-built. The site itself is not, exactly: its markup, its styles and its prose were drafted by a language model from prompts, then read line by line, corrected and pushed by hand. This page is the full account of that arrangement — what came from a prompt, what came from a person, and what went wrong in between.

01

What "vibecoded" means here

The word in the footer is not a disclaimer about the projects. It is a description of the pages you are reading.

Every card, every project page and every sentence about a game or a tool describes software that was written by hand. The description is a different matter. The HTML, the CSS, the fist drafts of the copy and the small filter script were generated by a model from prompts, then edited, tested and committed by a person. That is the whole claim: the site about the work, not the work.

  • From a prompt — page structure, class names, the first draft of every paragraph, the filter script, this page and the 404.
  • From a person — the decision to be plain about it, every fact about a project, the edits that removed overclaiming, and the final read before each push.
  • From the projects themselves — their READMEs and source, which is where the specifics come from. If a claim on this site is wrong, the repository is right and the page needs fixing.
02

The loop, in five steps

The same shape every time, whether the task was a whole page or one line in the footer.

Prompt
Describe the page, the audience and the constraints: static files, no build step, no trackers, nothing that breaks the live demos on their own Pages sites.
Draft
The model writes the markup and the prose in one pass, in the voice of the pages already there.
Read
Every line, against the project's actual README and source. This is where invented specifics get caught.
Test
A local server, every internal link, the HTML balance, and a byte-for-byte comparison of what shipped against what was tested.
Ship
A commit, a Pages rebuild, then the live pages fetched again to check the footer, the links and the content types.

None of that is exotic. It is the ordinary loop of building a static site, with one step added — reading a draft that arrived fluent and might still be wrong.

03

What the model got wrong

A model is fast, well-read and completely unbothered about whether a sentence is true. The corrections are the interesting part.

  • It invents specifics. Fluent numbers, plausible features, a confident detail that appears nowhere in the repository. The rule that came out of it: no specific survives without a source. Every claim about a project was checked against its README or source before it shipped.
  • It overcorrects in public. The first version of these hints was a banner announcing the whole thing. It was cut back to a word in the footer, a meta tag, a comment, humans.txt and a line in the console — five quiet signals instead of one loud one.
  • It reaches for new CSS. It wrote rules for the footer note before noticing that <abbr> already draws the dotted underline and the tooltip. Those rules were deleted. The only rule the hint still needs is the one that makes the word a link, so it opens this page on a phone as well as a desktop.
  • It has habits. Em dashes, three-part lists, "not this but that". Some were kept because they fit the voice of the site. Some were cut. This sentence is an example of the problem.
  • It breaks relative paths. Pages under /p/<slug>/ need root-absolute asset links. The first draft used relative ones, and the stylesheet quietly 404'd on every project page.

The model can write the sentence. It cannot know that a game has four weapons unless someone checks. A person still has to care whether the page is true — that is the part that does not automate.

04

The tells, and where they are

Six places, none of them a banner. If you found this page, you probably clicked the word in the footer.

  • The footer word — vibecoded, dotted and tappable, on every page. It links here.
  • A meta tag — <meta name="generator" content="vibecoded — prompted by a human, typed by a model"> in the head of every page.
  • A comment — one line in each page's <head>, for anyone who views source.
  • humans.txt — the classic colophon file, listing the human who prompted and the machine that typed.
  • The console — a small neon badge logged on the home page, for whoever opens devtools.
  • The About section — a single line under the toolbox list, saying the projects are hand-built and this site about them is not.

Quiet on purpose. A site can be honest about how it was made without making that the headline — the headline is still seven things worth playing with.
